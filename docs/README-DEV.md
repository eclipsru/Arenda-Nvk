# Ива — памятка для работы с проектом (для разработчика и агента)

Коротко: как запускать проверки, где точки отката, что можно и чего нельзя. Если через месяц вернётесь к проекту — начинайте отсюда.

---

## 1. Проверка перед любыми изменениями одной командой

```bash
bash tools/check.sh          # или: npm run check
```
Что делает (ничего не меняет):
1. проверяет окружение (node, python3, ветка, коммит);
2. сканирует репозиторий на секреты (токены, пароли, `.env`, keystore, приватные ключи);
3. проверяет согласованность релиза: `app-update.json` ↔ APK-файл ↔ эталонный хеш в тестах;
4. гоняет статические тесты (`tests/syntax-and-release.cjs`, `tests/email-guard.cjs`);
5. поднимает локальный сервер и гоняет браузерные тесты Playwright, если он установлен;
6. печатает итог: пройдено / ошибок / пропущено.

**Если Playwright не установлен:**
```bash
npm install
npx playwright install chromium
```

## 2. Снимок состояния (перед этапом и после)

```bash
bash tools/snapshot.sh                 # снимок без тега
bash tools/snapshot.sh --tag p0-done   # снимок + локальный тег точки отката
```
Складывает в `.snapshots/` (в репозиторий не попадает): ветку, коммит, `git status`, веса файлов, копию `app-update.json`, хеши APK. Ничего не коммитит и не отправляет на сервер.

Тег на GitHub отправляется **только по согласованию с владельцем**: `git push origin <тег>`.

## 3. Контроль «дизайн не менялся»

```bash
npm run screens         # снять эталон (только один раз или при осознанном изменении дизайна)
npm run screens:check   # сравнить со эталоном (расхождения по stable-страницам)
```
- Картинки: `.snapshots/screens/` (в репозиторий не попадают).
- Манифест с хешами: `tools/screens-baseline.json` (в репозитории, маленький).
- Сравниваются только `stable`-страницы (оферта, правила, app.html, 404, регистрация). Страницы с лентами и данными сравниваются глазами — они зависят от содержимого базы.
- Хеши воспроизводимы в одном окружении (одна машина/один образ). Если сравниваете из другого окружения — расхождения возможны из-за шрифтов; в этом случае смотрите картинки глазами.

## 4. Правила веток, тегов и откатов

| Элемент | Правило |
|---|---|
| `main` | **никогда не коммитить напрямую**. Публикация — только merge по решению владельца |
| `work/pN-...` | ветка этапа. Один этап — одна ветка — один Pull Request |
| тег `pN-done` | точка отката после приёмки этапа (создаётся локально, отправляется по согласованию) |
| откат кода | `git revert <коммит>` или переключение ветки; удаления файлов — только `git revert`, не `rm` |
| откат данных | только из бэкапа (см. `docs/BACKUP-SUPABASE.md`), и только после подтверждения владельца |
| откат релиза приложения | вернуть прошлую версию в `app-update.json` (файл предыдущего APK остаётся доступным) |

Правило миграций: только `create ... if not exists` / `add column if not exists` / `create or replace`.
Запрещено без письменного согласия: `drop`, `truncate`, массовые `update` без `where`. В конце файла миграции — закомментированный блок «ОТКАТ».

## 5. Чего в проекте делать нельзя (зафиксированные ограничения)

1. Не менять дизайн сайта и приложения: используется только `assets/theme.css` и существующие компоненты. Любое визуальное изменение — предложение, а не факт.
2. Не применять миграции к боевой базе без подтверждения владельца (миграции отдаются текстом, применяет владелец).
3. Не просить и не хранить секреты: `service_role`, пароль базы, пароль keystore, `.env` — в репозиторий и в чат не попадают.
4. Не парсить чужие сайты (2ГИС, Яндекс, Авито) и не делать массовых рассылок.
5. Не выводить на сайте выдуманные числа (счётчики «N ждут») — только реальные данные.
6. Не расширять сбор персональных данных без решения владельца (статус вопроса — см. `docs/ЖУРНАЛ.md`).

## 7. Две команды, которые чаще всего нужны владельцу (Windows)

```powershell
# 1. Бэкап базы (спросит строку подключения)
powershell -ExecutionPolicy Bypass -File tools\backup-windows.ps1 -Baseline

# 2. Смена пароля ключа подписи приложения (спросит пароли)
powershell -ExecutionPolicy Bypass -File tools\rotate-keystore-windows.ps1
```

Если `pg_dump` не установлен (например, `winget` падает с ошибкой 403 — это его известный баг), установка не нужна:
- структура базы — запрос `tools/schema-dump.sql` в SQL-редакторе Supabase;
- данные — `powershell -ExecutionPolicy Bypass -File tools\backup-api-windows.ps1`;
- либо портативный `pg_dump`: распаковать архив `…windows-x64-binaries.zip` и указать папку через `-PgBin`.
