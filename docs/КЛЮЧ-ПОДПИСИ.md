# Ключ подписи приложения «Ива» — памятка владельцу

> Решение владельца №22 (05.10.2026, вариант А): новый ключ **№6**. Владелец создаёт его **сам на своём компьютере**
> скриптом `tools/new-signing-key-windows.ps1` (встроенные средства Windows, ничего устанавливать не нужно) —
> ключ не проходит ни через чат, ни через песочницу агента.
> Эталон проверки: `5D2B9F8BB54AD0B816A779B5991746957EBD6FA056D8A63D1D1635077BED5DDE`
> (отпечаток сертификата ключа №6, НЕ секрет; вписан по первой проверке 05.10.2026, run 37242774621).
> Имя ключа внутри (alias) выдала Windows: `te-02013c21-5a1d-437c-836d-12e58ed47252` — проверка и сборка находят его сами.

## Что это такое — простыми словами
Ключ подписи — это «печать» приложения. Каждая версия приложения заверяется этой печатью.
Телефон ставит новую версию **поверх** старой, только если печать та же самая.
- Потеряли ключ или пароль → новые версии поверх не встанут, всем придётся переустанавливать (это и случилось с ключом №5).
- Чужой получил ключ **и** пароль → может выпустить «обновление» от вашего имени. Поэтому ключ и пароль — секреты.

Ключ состоит из двух частей, и нужны **обе**:
1. **файл ключа** (`1-iva-release.pfx`; его копия текстом — `2-key-text-for-GitHub.txt`);
2. **пароль** (`3-password.txt`, 24 знака).

Всё это скрипт кладёт в папку **`KLUCH-IVA-2026` на Рабочем столе**.

## Где ключ должен лежать (и больше нигде)
| Место | Что там | Зачем |
|---|---|---|
| **Секреты GitHub** (Settings → Secrets and variables → Actions) | `ANDROID_KEYSTORE_B64` = текст ключа, `ANDROID_KEYSTORE_PASS` = пароль | Отсюда GitHub сам подписывает новые версии. Значения никто не видит — даже вы и агент |
| **Резервная копия 1** — флешка (лучше отдельная, хранить дома) | папка `KLUCH-IVA-2026` целиком | Если что-то случится с GitHub |
| **Резервная копия 2** — облако (Яндекс Диск / Mail.ru Облако) **в архиве с паролем** | те же 3 файла в zip/7z с паролем | Если потеряется флешка |
| **Менеджер паролей** (или пароли браузера) | пароль ключа + отметка «ключ подписи Ива №6, файл на флешке и в облаке» | Чтобы пароль не потерялся, как с ключом №5 |

**Нельзя:** присылать файл или пароль в любой чат (в том числе агенту), класть в репозиторий
(он открыт всем — сторож `tools/check.sh` такое ловит), пересылать по почте/мессенджерам без архива с паролем,
хранить пароль в одном файле рядом с ключом без защиты, двойным щелчком «устанавливать» файл в Windows.

## Текст ключа = полная копия файла
Файл `2-key-text-for-GitHub.txt` — это тот же ключ, записанный текстом. Если файла `.p12` нет, его можно
восстановить из текста одной командой PowerShell (спросит путь к текстовому файлу, положит ключ на Рабочий стол):
```powershell
$t=(Read-Host 'Путь к файлу 2-key-text-for-GitHub.txt').Trim('"'); [IO.File]::WriteAllBytes("$HOME\Desktop\iva-release-restored.pfx", [Convert]::FromBase64String((Get-Content $t -Raw).Trim())); 'Готово: iva-release-restored.pfx на Рабочем столе'
```
Поэтому для резервной копии достаточно двух текстовых файлов: текст ключа и пароль.

## Как обращаться с ключом
- **Обычная работа:** ничего делать не нужно. Агент собирает версию, GitHub подписывает ключом из секретов.
- **Проверить, что ключ в GitHub правильный:** Actions → «Проверка ключа подписи» → Run workflow
  (кнопка появится после слияния в main; до этого проверку запускает агент). Ответ «✔ НОВЫЙ ключ №6 … = эталон» — всё в порядке.
- **Раз в полгода:** убедиться, что флешка читается и пароль из менеджера открывает архив в облаке.
- **Сменить пароль ключа** не обязательно (пароль случайный, 24 знака, нигде не публиковался).
  Если всё же понадобится — попросить агента: он сделает это через GitHub без смены «печати».

## Если что-то пошло не так
| Ситуация | Что делать |
|---|---|
| Пароль или файл куда-то утекли (прислали в чат, загрузили в репозиторий) | Сразу сказать агенту. Секреты GitHub не трогать до разговора. Решаем: новый ключ (снова одна переустановка у всех) или смена пароля |
| Потеряли флешку | Сделать новую копию из облака. Ключ менять не нужно, если флешка без подписи «что это» и пароль не был рядом |
| Удалили секрет в GitHub | Положить заново из резервной копии (текст из файла 2, пароль из файла 3) |
| Потеряли **всё** (и копии, и пароль) | Новый ключ, у всех одна переустановка. Аккаунты и заявки на сервере не пропадут |

## Как это было сделано (05.10.2026)
- Сначала агент создал ключ в своей песочнице, но передать его владельцу безопасно не удалось: этот чат не показывает файлы вне репозитория, а репозиторий открыт всем. Тот ключ **ни разу не использовался и уничтожен** (`shred`).
- Поэтому ключ создаёт владелец сам: `tools/new-signing-key-windows.ps1`. Скрипт делает сертификат RSA 4096 / SHA-256 на 30 лет и выгружает его в `.pfx` со случайным паролем из 24 знаков. Копию ключа из хранилища сертификатов Windows он удаляет. Текст ключа и пароль кладёт по очереди в буфер обмена, чтобы владелец вставил их в секреты GitHub, а потом открывает папку для резервных копий.
- Проверка ключа: `.github/workflows/keystore-check.yml`. Пока эталон `PENDING`, она сообщает отпечаток нового ключа; агент вписывает его сюда и в проверку. Сторож `tests/keystore-check-guard.cjs` следит, чтобы эталон в проверке совпадал с памяткой.
- Старый ключ №5 (файл у владельца, пароль утерян): **файл не удалять**. Если пароль когда-нибудь найдётся, он пригодится для разбора.
